## 이사를 결정한 배경

### Bottom-Up 파서(Shift-Reduce)에 대해

2023년 12월 이래로 Bottom-Up(Shift Reduce) 파서를 줄곧 써왔습니다. SR 파서는 겉으로 드러나는 구현이 간단하다는 강력한 장점이 있습니다.

```
[ Evaluable Operator Evaluable ] -> Formula
```

지금까지 사용하던 파서는 위와 같이 문법을 표현합니다. 여러 노드의 나열이 특정 규칙을 만족한다면 하나의 노드로 축약합니다. 위에서 예시로 든 규칙은 '노드가 `값이 있는 노드` - `연산자` - `값이 있는 노드` 순서로 놓여있다면 `수식` 노드로 축약할 수 있다'라고 해석할 수 있습니다. 실제 파싱은 다음과 같은 순서로 진행됩니다.

1. 입력받은 토큰을 적절한 원시 추상 노드(실행 불가능)로 변환하고, '처리 해야 할 노드' 큐에 넣는다
2. **Shift** | 처리 대기 큐에서 노드를 하나 가져와서 파싱 스택에 넣는다
3. SR 파싱 룰을 파싱 스택에 대본다

- **Reduce** | 규칙에 매칭되었다면 노드를 축약하고 첫 SR 파싱 룰부터 다시 대본다
- 매칭되지 않았다면 다음 규칙으로 넘어간다

5. 더 이상 현재 스택에서 매칭되는 룰이 없으면 2번으로 돌아간다
6. 처리 해야 할 노드 큐가 비어있으면 파싱을 종료한다.

개념이 직관적이고 실제 구현도 간편합니다.

### Bottom-Up 파서의 문제

그러나 단점도 명확합니다.

1. 실행 가능한 상태로 파싱됨을 보장하지 못한다
2. 실제 AST에서는 존재해서는 안되는 추상 노드가 필요하다
3. 파싱 룰이 코드 맥락을 알 수 없다

1번과 2번이 가장 큰 문제였는데, Bottom-Up 파서의 특성상 최하위 단계에서 파싱이 흔들리면 프로그램 전체가 복구 불가능하게 망가졌습니다. 예를 들어서 다음과 같은 코드가 입력되었다면:

```
만약 이름: "홍길동" 이면
    "안녕 길동!" 보여주기
```

조건문, 출력문, 문자열은 올바르게 작성되었지만 동등비교연산자의 작성을 실패한 사례입니다. 이 코드를 SR만으로 파싱하면 조건문 전체가 조립에 실패하여

```
- '만약'이라는 이름을 찾을 수 없어요
- `:`는 실행할 수 없는 코드에요
- '이면'이라는 이름을 찾을 수 없어요
- 여기에서는 들여쓰기를 4칸 해야 해요
```

와 같은 오류가 발생했습니다. 사람이 보기에는 당연히 조건문인데, Bottom-Up 파서는 이를 알 수 없습니다. 조건문 축약 패턴을 `[ 만약 $condition 이면 #EOL $body]`라고 하면 `$condition` 자리에 단일 노드가 와야 하는데, `이름: "홍길동"`은 문법 오류라서 단일 노드로 축약해줄 규칙이 없습니다. 그래서 분명히 조건문을 의도했음에도 불구하고, 파서는 이를 알지 못해 트리 전체를 포기해버립니다. 파싱에 '실패'한 코드를 실행하려고 하면 위에 언급했던 2번 문제에 의해, 최종 결과에서는 사라졌어야 할 노드가 최종 단계에서도 남아있어 의미 없는 크래시를 냅니다.

## Top-Down 파서로 재구현

### 사람은 Top-Down으로 코드를 봄

```
만약 이름: "홍길동" 이면
    "안녕 길동!" 보여주기
```

다시 고장난 코드를 보면, 사람은 위 코드를 조건문으로 이해합니다. 조건문의 구조를 먼저 파악하고, 그 안에 들어가는 조건과 실행할 내용을 봅니다. 그 후 조건문의 문법이 이상하다는 생각을 하면, '조건문인데 조건절이 문법이 틀렸네'라고 생각합니다. 사람은 Top-down으로 코드를 봅니다. 구조를 보고 값을 보는데, 이를 본따서 Top-down으로 파서를 구현할 수 있고, 그 중 하나가 재귀하강 파서(Recursive Descent Parser, RD)입니다.

### 구문 규칙 예시

재귀하강 파서에서 조건문 규칙은 다음과 같이 표현됩니다.

```
[ IDENTIFIER(만약) ...$condition IDENTIFIER(이면) ]
```

코드 한 줄에 해당하는 토큰이 `만약`으로 시작해서 `이면`으로 끝나면, 해당 줄은 예외 없이 조건절로 해석됩니다. 그 후 `condition` 토큰을 값 파서에게 넘겨서 파싱을 수행하고, 문법/에 오류가 있었다면 AST 노드에서 기억하고 있다가 Validation 단계에서 보고합니다.

그러면 이제 고장난 코드에선 다음과 같은 오류가 납니다.

```
`:`는 실행할 수 없는 코드에요
```

코드 작성자는 이제 `만약`을 찾을 수 없다는게 무슨 뜻인지 고민할 필요가 없습니다. 전체 코드의 맥락을 볼 수 있게 되어, 정정이 필요한 코드만 식별해 작성자에게 보고할 수 있습니다.

단점이라면 SR 파서보다 덜 선언적입니다. 조건문 규칙을 의사코드로 나타내면 다음과 같습니다.

```
pattern = [ IDENTIFIER(만약)  ...$condition IDENTIFIER(이면) ]

func 조건문(line, parse, getBlock) {
    result = pattern(line)

    condition = parse(result.condition)
    block = getBlock()

    return Conditional(
      condition,
      block
    )
}
```

SR 파서와 달리 파싱의 본론은 함수에 있고, 위와 같이 단일한 조건문이 아니라 else도 구현해야 한다면

```
starting_pattern = [ IDENTIFIER(만약)  ...$condition IDENTIFIER(이면) ]
else_pattern = [ IDENTIFIER(아니면) ]

func 조건문(line, parse, get_block, get_line) {
    result = pattern.test(line)

    condition = parse(result.condition)
    block = get_block().consume()

    following_line = get_line()
    else_result = else_pattern.test(following_line.look)

    if else_result == null {
        return Conditional(
          condition,
          block
        )
    }

    following_line.consume()

    else_block = getBlock().consume()

    return Conditional(
      condition,
      block,
      else_block
    )
}
```

과 같이 상당 부분이 명령형으로 쓰어야 하며, `elif`와 같이 선형적으로 확장되는 문법이라면 명령형 파싱 본문은 계속 복잡해집니다.
